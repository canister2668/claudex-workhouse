# Known Limitations

[English](known-limitations.en.md) · [한국어](known-limitations.ko.md) · [日本語](known-limitations.ja.md)

Previous: [Testing](testing.en.md) · [Guidebook](guide.en.md) · Next: [License →](license.en.md)

- The public hostname is intentionally unpublished until real Cloudflare Team Domain and Application AUD values are configured and JWT validation passes.
- Claude read-only jobs expose only read/search/web tools. Standard conversation turns use `dontAsk` with those tools explicitly allowed; only explicit planning turns use `plan` mode.
- External Claude sessions are visibility-only; Claudex Workhouse cannot resume, fork, or stop them.
- Codex registration is eventually consistent. A newly returned job can remain `pending`, then become `unknown` after bounded reconciliation; manual refresh rechecks it without creating a duplicate.
- Claudex Workhouse owned Codex and Claude task details are Live through SSE. External CLI/VS Code Codex and external Claude output connections are not owned by Claudex Workhouse, so they are accurately shown as Delayed polling or History rather than fake Live output.
- The browser approval UI and server path are covered for `accept`, `acceptForSession`, and `decline`. A Playwright fixture follows the local Codex Push deep link into the question UI and clicks all three approval controls; server and authenticated Desktop-Worker fixtures verify task/host/workspace/risk fields, expiry rejection, duplicate handling, exact remote 400/409 approval errors, and `HOST_OFFLINE` without treating failures as approval or denial. This does not prove every future Codex app-server version or approval method: the native runtime must advertise the decision, and execution modes whose effective policy is `never` do not emit interactive approvals.
- Quota-reset reservations survive server restarts while waiting, and stale runtime `claiming`/`starting` rows are reconciled by the bounded reservation pump. If the server stops in the narrow interval after Provider launch begins but before the task row is durably confirmed, the reservation is marked failed and automatic retry remains blocked to avoid duplicate execution. After inspecting the Provider for an already-started task, the user may explicitly return that failed reservation to the waiting queue from its reservation card.
- Confirmed Claudex Workhouse-owned Worker process loss is offered as an explicit, reviewed resume in the task detail. The preview fixes the original Provider thread, execution host, Workspace, model, and permission boundary; a current host may only lower the permission, and a failed official resume is never replaced with a new session. Completed, explicitly failed, user-stopped, external, ambiguous, already-resumed, and superseded older thread tasks cannot launch this recovery action. A restart reconciles an unfinished recovery claim to the already-persisted resumed task when its attempt metadata proves the link; otherwise it records an uncertain failure and blocks automatic retry to prevent duplicate execution. The database and browser fixtures cover restart reconciliation, concurrent-click idempotency, exact boundary display, Worker host-restart classification, local Claude `unknown` reconciliation, and rejection of a mismatched remote thread, but a physical NAS power-loss exercise against both live Provider runtimes has not been performed.
- Full-history search merges the native Codex `thread/search` result with safely persisted Workhouse-owned Codex and Claude task fields. The current NAS SQLite 3.40.0 build has no FTS5 support, so the stored-task side uses an indexed `updated_at, id` cursor and examines at most 2,000 candidate rows per source page; it reads title, prompt, final result, and stored error, but never task logs or Provider transcript files. A page with no match can still have an older cursor, and the UI labels that bounded-range state separately. Each query returns at most 500 results. Search cursors are in-memory, capped, and expire after ten minutes or a server restart; restart the query when a cursor expires. Rows updated while paging may move ahead of the current cursor, so restart the query for a fresh snapshot. The fixtures cover an unloaded older Claude task, deterministic within-page Codex/Claude merge order, literal Korean and `%_` matching, positive and negative Provider/Workspace/status/date filtering, bounded scanning, and an exact stored output-card jump. External Claude CLI sessions are not included because Workhouse has no safely persisted prompt/result history for them; external Codex results come from the native search API. Native Codex only reports `running` or `unknown` status in the tested runtime, and native-only matches depend on its official snippet and available turn history, so completed/failed native status filtering and an exact card cannot be guaranteed when that runtime omits those fields or matching turn content.
- Full-history search is task/session history for Codex and Claude; collaboration/debate titles are not included. Stored-task scanning stops after 50,000 candidates per query. Native Codex search is used only when its shared app-server connection is already warm, so search cannot start a short-budget connection that disrupts other Codex views; while cold or unavailable, the UI explicitly labels its cached-title fallback.
- Custom prompt presets are single-user server settings capped at 20 entries, 40 Unicode characters per label, and 4,000 Unicode characters per prompt; longer prompts are rejected with an explanation rather than silently truncated, and built-in presets are not stored with them. A device migrates its legacy `deck-prompt-presets` value only when the server is empty and that device has no prior server snapshot. Later two-sided changes require an explicit server-value or merge choice: the last snapshot preserves deletions made on either side, and the server copy wins same-ID edit conflicts. Merge-limit exclusions and deletion exclusions are shown before saving. Invalid stored values are salvaged with a CAS update after the original value and revision are retained in `ui.prompt-presets.corrupt-backup`; the audit records kept and discarded counts. Sync runs at application startup, when opening task creation, and when a visible browser returns to the foreground; there is no background push channel for preset changes, and failed automatic uploads use a short cooldown. Browser fixtures use independent desktop, phone, and tablet contexts and cover one-time migration, explicit conflict merge, an already-open device refresh, HTTP failure key replacement, and lost-response idempotent recovery. They do not constitute a physical Safari/Android device exercise.
- PWA share intake stores title, text, URL, and accepted attachments behind an opaque expiring token, then opens an editable new-task draft without starting it. Unconsumed attachments are removed on token expiry; consumed files use the existing seven-day upload cleanup policy and the same type and size restrictions, including currently accepted executable or script file types. Unit fixtures cover same-origin and OS document-navigation metadata, cross-site rejection, manifest fields, and draft conversion, while Playwright covers the browser draft flow. This has not been exercised through a physical Android/iOS share sheet or through the production Cloudflare Access policy; browser header behavior and Access cookies on those devices therefore remain unverified.
- Pull-request creation is limited to completed Workhouse-owned tasks with a registered Workspace. It rechecks GitHub CLI authentication, the GitHub remote, named head branch, upstream/push state, open PRs, and the user-edited base branch on the execution host; it never pushes, merges, reviews, or force-pushes. The editable task outcome draft may contain paths or other sensitive task content, so the user must inspect it and explicitly confirm before publication. Server idempotency and an in-process per-task lock prevent duplicate clicks, but the lock does not survive a server crash; after an uncertain external `gh pr create` result, the next preflight relies on GitHub's open-PR query to reuse the PR. Unit tests use a fake `gh` executable and do not create a real external PR. The mobile UI fixture covers confirmation and response handling, but remote Worker operation has only protocol/unit coverage and requires a Worker version advertising the C6 PR commands.
- Codex 0.144.1 does not expose confirmed effective model/effort/service-tier values in the tested thread and turn responses. Claudex Workhouse shows requested values and leaves effective values as “unconfirmed”.
- `thread/items/list` is registered but unsupported in Codex 0.144.1. Turn pagination is used instead.
- The five existing `cx doctor` failures are stale dead-broker records outside Claudex Workhouse scope. Fourteen core version, hash, isolation, and routing checks pass; this change does not remove or hide those records.
- A Linux or Linux-based NAS Docker deployment is recommended for the main server. The Windows x64 portable server is a compatibility alternative and provides an intentionally unsigned portable ZIP with a SHA-256 sidecar. Authenticode publisher identity is not provided, so SmartScreen may show Unknown publisher. A clean non-administrator Windows 11 x64 VM must still verify packaging, Defender/SmartScreen behavior, NTFS/ACL behavior, redirected Downloads, Provider discovery and execution, interrupted update/rollback, and first boot before stable promotion.
- Running work survives browser, Tunnel, and Claudex Workhouse server restarts while its Worker process remains alive. NAS power loss or reboot still kills in-flight processes; after the service and Worker return, only tasks whose missing process is reconciled to a confirmed recoverable interruption can be manually resumed through the recovery action above. The DSM boot task running `bin/boot-start.sh` brings back the service itself (see [deployment](deployment.en.md)); it does not automatically resume agent jobs.
- If the external URL returns HTTP 502 after a reboot, the local origin is down: run `node bin/claudex-workhouse.mjs status` and `curl -sS http://127.0.0.1:3410/api/health/live`. A missing or disabled `Claudex Workhouse Startup` boot task is the usual cause; start it with `bin/boot-start.sh` and re-check the task in Task Scheduler.
- PWA offline support is an application-shell/error experience only. Task content and results are never cached for offline reading.
- DSM boot task creation and Cloudflare dashboard changes require manual administrator action. `esynoscheduler.db` is root-owned, so the boot task must be created in the DSM UI; the boot wrapper and docs are prepared, but the task registration cannot be scripted from an unprivileged service account.
